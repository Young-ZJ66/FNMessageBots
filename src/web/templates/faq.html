常见问题

1. 渠道说明

查看：notification-channels.md

2. 忘记密码

编辑配置文件 config/config.json，删除 web_password_salt 和 web_password_hash，然后重启应用。 重新设置密码时：应用市场版从飞牛桌面打开（NAS 管理员身份）可直接设置；其他方式访问需要填写初始化码，可在应用运行日志中查看（Docker 版执行 docker logs 容器名），或查看配置目录下的 .setup_code 文件。 手装 Docker 也可在 compose 中设置环境变量 FNMB_WEB_PASSWORD（至少 8 位）作为初始密码。

3. 升级后要求设置密码 / 填写初始化码

旧版曾支持关闭密码验证（web_password_enabled: false）。新版本已强制鉴权，该开关失效。 若你之前关掉了密码验证、又从没设过密码，升级后第一次打开配置页会要求设置访问密码，并填写初始化码。 Docker 版请执行 docker logs 容器名（容器名以你的 compose 为准，常见为 fn-message-bots），在日志中查找「首次设置密码需填写初始化码」一行；也可查看配置目录下的 .setup_code 文件。 填入初始化码并设置密码（至少 8 位）后即可进入；也可在 compose 中设置环境变量 FNMB_WEB_PASSWORD 预置初始密码后重启容器。

4. 无法安装

目前存在部分用户在应用市场无法安装，提示 python 异常或 pip 异常。这个问题受系统环境影响，暂时无法完全规避。 可尝试： 一：直接使用 Docker 版本，通常可稳定安装运行。 二：切换系统下载源，并开启科学网络，多尝试几次，大概率可下载 python 成功。

5. Docker 名称和应用市场名称

飞牛应用市场名称：日志推送 Docker 镜像名称：fn-message-bots 说明：应用市场版为原生运行（非 Docker 容器）；Docker 版需手动部署，便于环境受限时安装。手装 Docker 默认 Web 端口 18080，应用市场版为 18230。Docker 镜像通常会先发布（修复与功能更新更快），稳定后再提审飞牛应用市场，所以应用市场版本一般会比 Docker 晚约一周。

6. 排查问题优先看日志

排查问题建议先确认飞牛日志是否与推送内容一致；若不一致，再定位为项目侧问题。 如果你希望新增推送格式，请尽量附上数据库记录格式和日志截图，便于快速支持。

7. 关于备份库 / 影视 / 照片事件说明

备份库 / 影视 / 照片事件默认不勾选，需要时请手动开启。 它们对应不同数据库，只有勾选对应推送事件时，项目才会轮询对应数据库；未勾选则不会轮询。

8. 遇到问题 / 想提需求

请到项目仓库提交 Issue。为便于定位，麻烦附上：启动日志里的 [schema 自检] 行、docker compose logs 中的报错、以及相关事件的原始日志（配置页可查看推送记录）。

9. 端口与访问方式

Docker 版默认端口：18080（可自行修改），首次访问需设置访问密码。 应用市场版：请从飞牛桌面图标打开，经飞牛统一网关访问（地址形如 https://NAS地址/app/FnMessageBot/），沿用 NAS 登录态，仅 NAS 管理员可访问；端口 18230 只监听本机 127.0.0.1，局域网无法直连。

10. SSH 登录推送没有了？

飞牛新版本里，主日志库 logger_data.db3 往往不再写入 Sshd* 事件，且系统已取消 /var/log/auth.log。 本应用改为轮询宿主机 journalctl -u ssh / sshd 采集 SSH 登录成功、失败、无效用户与断开。

应用市场原生版：进程直接跑在宿主机，一般无需额外挂载；请确认系统有 journalctl 且应用以足够权限读取 journal（默认 root）。

手装 Docker 版请确认已挂载：

- /var/log/journal:/var/log/journal:ro
- /run/log/journal:/run/log/journal:ro
- /etc/machine-id:/etc/machine-id:ro

Docker 镜像需包含 journalctl（官方镜像已安装 systemd）。宿主机可先自检：

sudo journalctl -u ssh -n 20 --no-pager

若 journal 可读而推送仍无，请查看应用日志是否出现「SSH journal 轮询已启动」。journal 不可用时会回退尝试主日志库中的 Sshd*（若库中仍有）。

11. 测试推送没问题，但是无法推送日志消息

这个问题大概率是数据库存在异常。可先查看应用运行日志，是否提示：数据库查询失败：database disk image is malformed。 如果出现这个提示，基本可以判定是日志数据库损坏或（Docker 版）数据库挂载失败；再检查日志显示是否正常，大概率是日志数据库的问题。 修复命令（仅供参考，建议通过 SSH 执行）： sudo -i systemctl stop eventlogger_service rm /usr/trim/var/eventlogger_service/logger_data.db3 chown -R trim:trim /usr/trim/var/eventlogger_service/ systemctl start eventlogger_service systemctl status eventlogger_service

12. 挂载影视库 / 相册提示权限问题

Docker 版：请在编排文件（如 docker-compose.yml）中自行添加卷挂载，使容器能访问宿主上的影视 / 相册数据路径；权限与 UID/GID、挂载只读等均在您本机配置中处理。 应用市场版：若读取影视 / 相册相关数据库时报权限不足，可在 SSH（root）下按需执行下列命令。请自行评估放宽目录权限、数据库文件权限以及 ACL 带来的安全风险（例如更多用户可进入目录或读取数据库文件）；系统需支持 setfacl（ACL），否则请先安装/启用相关功能。 

sudo chmod 755 /usr/local/apps/@appdata/trim.media/database /usr/local/apps/@appdata/trim.photos/db
sudo chmod 644 /usr/local/apps/@appdata/trim.media/database/*.db* /usr/local/apps/@appdata/trim.photos/db/*.db* 2>/dev/null

sudo setfacl -m u:FnMessageBot:rx /usr/local/apps/@appdata/trim.media/database
sudo setfacl -m u:FnMessageBot:r /usr/local/apps/@appdata/trim.media/database/trimmedia.db
sudo setfacl -m u:FnMessageBot:r /usr/local/apps/@appdata/trim.media/database/trimactivity.db
若相册侧仍有权限错误，可对 trim.photos/db 下实际使用的 .db 文件按同样方式为 FnMessageBot 增加只读 ACL（示例：sudo setfacl -m u:FnMessageBot:r <文件路径>）。

说明：原生版直接访问宿主机路径；Docker 版还需在 compose 中挂载对应目录。程序需要知道数据库文件路径：若 config.json 中对应字段为空，会按常见 NAS 路径自动探测；在 Web 页保存配置后，探测到的路径会写入 config.json。若仍提示未找到库，请核对下列字段（路径按 NAS 实际为准）：

  "logger_db_path": "/usr/trim/var/eventlogger_service/logger_data.db3",
  "backup_db_path": "/usr/trim/var/backup_service/basic_backup.db3",
  "media_lib_logger_enabled": false,
  "media_lib_service_patterns": ["mediadb", "trimmedia"],
  "media_lib_app_name_patterns": ["影视"],
  "trim_media_db_path": "/usr/local/apps/@appdata/trim.media/database/trimmedia.db",
  "trim_activity_db_path": "/usr/local/apps/@appdata/trim.media/database/trimactivity.db",
  "photo_db_path": "/usr/local/apps/@appdata/trim.photos/db/photo.db",
  "scheduler_db_path": "/var/apps/fn-scheduler/var/scheduler.db"

若命令执行以后仍然无效，可以尝试卸载重装。

13. Docker 容器事件与 docker.sock 权限

在监控事件中勾选「Docker 容器」相关事件后，保存时若出现「无法访问 /var/run/docker.sock」类告警，说明当前进程无权读写 Docker Engine 的 Unix socket。若你在 config.json 中配置了 docker_socket_path，以下命令中的路径请改为与你配置一致。

安全提示：将用户加入 docker 组或使用 ACL 读写 docker.sock，等同于授予通过 Docker API 操控引擎的能力；请仅在理解风险后操作，勿随意 chmod 777。

自建 Docker / Compose：仅挂载 docker.sock 不够——还需让容器内正在运行的 Python 进程对 socket 具备读写权限。宿主上常见为 srw-rw---- root docker（660），非 root 进程须加入 docker 组对应的 GID。在 NAS SSH 执行 stat -c '%g' /var/run/docker.sock 得到数字 GID，在 compose 中示例：

    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
    group_add:
      - "999"   # 改为你上一步得到的 GID
# 修改 group_add 后须 docker compose up -d 重建容器，仅重启进程无效。

若镜像以非 root 用户运行且无法改组，可临时 user: "0:0" 验证（请自行评估安全风险）。

应用市场版（SSH，默认路径示例）：

# 查看 socket 权限（SSH root）
ls -l /var/run/docker.sock
# 常见：srw-rw---- root docker（仅 root 与 docker 组成员可读写）

# 将应用运行用户加入 docker 组（用户名以 ps 为准，一般为 FnMessageBot）
sudo usermod -aG docker FnMessageBot
# 加入组后必须完整关闭并重启本应用，新进程才可能带上 docker 组。

# 若重启后进程仍无 docker 附属组（部分 NAS 环境），可权宜对 socket 使用 ACL（自行评估风险；Docker 重启后 socket 可能被重建）
sudo setfacl -m u:FnMessageBot:rw /var/run/docker.sock

# 验证（重启进程后再执行）
sudo -u FnMessageBot test -r /var/run/docker.sock -a -w /var/run/docker.sock && echo OK || echo NO
# 输出 OK 后再回 Web 保存配置；告警应消失。

若仍提示无权限，可用 grep '^Groups:' /proc/<PID>/status 与 getent group docker 对照，确认运行中的 Python 进程是否包含 docker 组的 GID；仅用户账号在 docker 组中、但进程附属组未加载时，需依赖平台行为或上述 ACL 等权宜方式。

14. 升级后「魔法推送」「企业微信应用」渠道不见了，原配置还在吗

2.7.0 起推送渠道收敛为企业微信、钉钉、飞书、通用 Webhook 四个，「魔法推送」「企业微信应用」等已移除。若仍需要：魔法推送本质是 HTTP 接口，可用「通用 Webhook」填 http://魔法推送地址/api/push/你的Token，请求方式 POST、内容类型 json、请求体 {"title":"{title}","content":"{content}","type":"text"}。

旧渠道的残留配置键会被忽略并在启动日志中提示「可安全删除」；下次保存配置时自动从 config.json 清理。
